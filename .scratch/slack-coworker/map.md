# Map: Slack coworker agent

Label: `wayfinder:map`

## Destination

A **buildable v1 spec** for an open-source, self-hosted AI coworker that lives in Slack — every architectural question answered and v1 scope sharp enough to hand to `/to-spec` → `/to-tickets` → `/implement`. The map produces decisions, not code; the build happens after, in fresh sessions.

v1 is done when a self-hoster can: @-mention the bot in a thread, walk away, and come back to a completed piece of real work — where "real work" spans its Obsidian-style notes, its accumulated memory of you, and live GitHub and Linear data.

**The spec exists**: [`spec.md`](spec.md) (`ready-for-agent`) — synthesised from the eleven resolved tickets and five ADRs.

**The build tickets exist**: fifteen tracer-bullet slices in [`build/`](build/), numbered in dependency order. Two were added after charting: [`build/14`](build/14-file-ingress-from-slack.md) carries raw data into a Job, and [`build/15`](build/15-skills.md) adds human-authored procedures for non-MCP capabilities. Kept separate from `issues/` so decision tickets and work tickets do not share a numbering line.

**Amended 2026-07-30: GitHub is an ordinary MCP connector.** The intermediate GitHub
App plus `gh` Skill design in ADR-0006 introduced a second configuration model,
authentication lifecycle, preflight path, audit path, and capability mechanism without
ever reaching an end-to-end Job. [ADR-0007](../../docs/adr/0007-github-is-an-official-mcp-server.md)
supersedes it and restores [ADR-0005](../../docs/adr/0005-connectors-are-mcp-config.md):
GitHub, Linear, and third-party connectors are entries in one `mcp.json`.

GitHub uses the official remote MCP server with a fine-grained PAT restricted to the
repositories and permissions the instance needs. Server toolset/exclusion headers,
the project fixed disabled-tool floor, and per-instance `disabledTools` keep known merge
and deletion operations out of the tool surface. Tool inventories are not pinned; upstream
additions and removals are accepted so connector evolution does not become an outage.

The repository seam is again **local `git` for checkout, edits, tests, and push; MCP for
GitHub metadata, issues, reviews, and pull-request creation**. Skills remain useful for
systems without an MCP server but are not a parallel connector architecture. The current
sequence is **08 → 09 → {10, 12} → 11 → 13**; build/15 is independent.

**Build/04 left one thing unfinished on purpose, and moved it rather than solving it twice.** Write records are classified from the engine's event stream, which sees file changes and MCP tool calls exactly and shell commands only by pattern — so a Note written with `cp` or `rm` leaves no record. [`build/07`](build/07-the-vault.md) gained a criterion for it, because echoing Note diffs needs a before-and-after snapshot of the Vault anyway, and a snapshot that can diff can also catch what nothing recorded. Measuring the engine first also reshaped the ticket twice: shell calls arrive as `/bin/zsh -lc "…"` with whole `&&` chains in one item, so one command can produce several records — and a chain's exit code cannot say *which* part of it failed, which is why a record states what is known rather than claiming an attempt failed.

**Build/05 measured what "hard-stop" actually reaches, and it is less than the phrase suggests.** Aborting the run kills the Codex process — verified against a real `codex exec` — but a shell command Codex had already launched is reparented to init and keeps running, because the process it spawns is not a group leader and the SDK exposes no way to kill the group. Configured limits still bound model spend (the model is only ever called by the process that died) and side effects are not, which is the same caveat the Job's own report already carries. **Amended 2026-07-30: the per-Turn timeout, Turn cap, and token budget are opt-in and disabled by default.** Recorded in [`build/05`](build/05-bounds-and-failure.md#the-limit-on-what-stop-means) and pinned by a contract test in the style of the session-storage one: if it starts failing, upstream fixed it.

**Build/06 took that bound and let Slack choose its number.** A Job's status message can be rewritten twelve times a minute and `chat.update` is Tier 3 — roughly fifty a minute, *per app rather than per Job* — so the instance ceiling is **four concurrent Jobs**, which is where the arithmetic stops rather than where a laptop does. The queue itself is a lane per Thread under that ceiling: places are claimed synchronously so arrival order survives, and a Job that waited **takes over its own queue receipt** as its status message rather than posting a second one. Two decisions were made that the ticket did not ask for and both are in [`build/06`](build/06-queue-at-turn-boundary.md#comments): **hard-stop now empties the Thread's queue** and says what it dropped, because a stop followed by the next queued Job starting immediately reads as a stop that did not work; and a queued Job is **told in its prompt that it was queued**, because otherwise "actually, use the other repo" reads as a fresh request about work it considers finished. Still open and now sharper: **a queued mention does not survive a restart** — Slack has been ack'd and the queue is in memory, so three queued mentions die silently, which is worse than the interrupted-Session case a running Job leaves behind.

**Build/07 made the Vault the memory, and closed build/04's gap from the filesystem rather than from the event stream.** A Note's Write record is now made by comparing the Vault's contents before and after the Job, which catches a Note written with `cp` or `rm` and carries the diff that [ticket 10](issues/10-memory-poisoning.md) made the actual control over poisoning — so `writes/classify.ts` deliberately records *nothing* for a file inside the Vault, and five existing tests had to start writing real files. **The accepted cost is ordering**: a diff cannot exist until the Job is over, so Vault records arrive as a block at the end. The Librarian is a **one-off Session** the wrapper never resumes, added to the engine port as `startOneOffSession` — it is handed the transcript precisely because it does not share the Session, which is the tell that it must not be a second Turn in the Thread's. **The answer is posted before the pass runs and the pass's Notes are recorded after it**, so ordering stays chronological and a slow tidy-up delays nobody — the spec's "already done *and reported*" settles that. Two decisions the ticket did not ask for are in [`build/07`](build/07-the-vault.md#comments): **a late stop kills the curation without turning a finished Job into a stopped one**, and **provenance is stamped by the wrapper rather than written by the model**, because the one field saying "this came from the coworker" is the one field the coworker could forget or fake. **The measured limit is attribution**: there is one Vault and four concurrent Jobs, and nothing in the filesystem says which Job wrote a file — so a Job whose window overlapped another's records its findings as *possibly another Job's* and leaves `thread:`/`job:` off the frontmatter, because the two correct fixes each cost more than the problem (a Vault lock serialises the Jobs build/06 runs at once; a per-Job view stops the Vault being one directory a human owns). Still open: **nothing bounds the Librarian's spend** — its Turn and tokens are counted against its own five-minute clock and against no budget.

**Build/15 built the Skills mechanism and found that the ticket's own mechanism was impossible, which corrected [ADR-0004](../../docs/adr/0004-root-note-is-links-only.md) a second time.** The amendment said "the wrapper refuses agent writes to the Skills location". No such refusal can exist: the Root note is enforceable because it is *injected*, and Skills are never injected — they are read from disk on demand, so the wrapper is never in the path. **What enforces it is the sandbox's writable list, and that forced the layout rather than being satisfied by it**: since a read-only subtree of a writable root is not expressible, the Vault's writable grant moved down a level to `<vault>/Notes` and Skills became its sibling at `<vault>/Skills`, with the *parent* being what a human opens in Obsidian — so both halves stay in one vault and wikilinks reach from a Note to a Skill unchanged. Measured against Codex 0.145.0 rather than assumed, and it is **stronger than the ticket expected**: the shell is refused by the kernel (`operation not permitted`, exit 1), not merely by Codex's own tooling (`patch rejected: writing outside of the project`), so a prompt injection cannot argue with it. **The measurement's near-miss is the more valuable finding.** The first probe reported no boundary at all — it was sited in `$TMPDIR`, which `workspace-write` grants *unconditionally* whatever the writable list says. So a temporary Skills location is a **fatal** startup condition rather than a warning (it voids the authorship rule while leaving an instance that works perfectly), the test harness had to move out of `os.tmpdir()` entirely, and **an existing contract test turns out to have been asserting nothing** — build/07's "writes into the Vault outside its workspace" sited its Vault in the temp directory, so its write would have succeeded whether `additionalDirectories` worked or not. It has only tested that mechanism since this ticket. Two decisions the ticket did not ask for are in [`build/15`](build/15-skills.md#comments): **a broken layout throws and a leaked credential only warns** — one is the project failing to deliver its own guarantee, the other is the self-hoster's credential in their own vault, and the scan is documented as a lint rather than a boundary — and **the coworker is told the directory is read-only and told what to do instead**, because the failure mode of silence is a Job spending a Turn failing to save an edit and reporting that as the work. One substitution is stated plainly: the database Skill ships and the *mechanism* is pinned end to end against a real `codex exec`, but no live `psql` has ever run, so the Skill's content is example prose that has never met a real schema.

**One criterion has been struck rather than met**, and it is worth knowing before the remaining tickets lean on it. Build/02 measured whether a Job can read Codex's own session storage, and it can: under `workspace-write` filesystem reads are unrestricted, and `codex exec` exposes no way to narrow them. So ADR-0003's "Sessions never read each other" holds for what the engine *loads* but is behavioural, not structural, for what the agent can *go and read* — the same class of finding as the branch-protection measurement in ADR-0002, and it needs the same treatment: an amendment stating the guarantee at its measured strength. Details and the rejected fixes are in [`build/02`](build/02-session-per-thread.md#the-one-criterion-that-failed-session-storage-is-readable).

## Notes

**Domain.** A Slack-native AI coworker. Human-initiated, long-running delegated work. Distributed as open source; each user self-hosts their own instance against their own workspace and their own tokens.

**Settled while charting** (these fix the scope; reopening one redraws the map):

- **Audience** — open source, others self-host. Not multi-tenant SaaS. Consequences: configuration over hardcoding, connectors as a real plugin interface rather than a pile of if-statements, and a setup story someone else can follow without you in the room. **Independently confirmed by the Slack research**: non-Marketplace distributed apps are throttled to 1 `conversations.replies`/minute, while internal customer-built apps are exempt — so "create your own app from this manifest" is the only configuration that actually performs, not just the open-source convention.
- **"Full AFK" means delegate-and-walk-away.** Always human-initiated: you @-mention it with a real task, it works for minutes or hours, it reports back in the thread. Needs durable long-running jobs and progress reporting; needs no event ingestion and no scheduler. The other two senses of AFK — unsupervised action, and acting unprompted — are fog and out-of-scope respectively.
- **v1 scope is all four capabilities**: the Slack thread spine, Obsidian-style notes, evolving memory, and GitHub + Linear connectors.
- **Stack is TypeScript.** Slack's Bolt SDK is first-class in TS, MCP has strong TS tooling, and contributors can pick it up. Note the TypeScript codebase is the *Slack-and-orchestration layer*; the agent itself is a separate process (see the engine decision below).
- **Engine is Codex CLI, driven via `codex exec` and `@openai/codex-sdk`** — confirmed against verified capabilities, no longer conditional. See [ADR-0001](../../docs/adr/0001-codex-cli-via-exec-and-sdk.md). The architecture is a **wrapper around a subprocess**, not a host for an agent loop. Two consequences that constrain everything downstream: the stack is **effectively OpenAI-only** (`WireApi` has one variant; "bring your own model" needs a Responses-API backend), and the coworker **cannot ask permission** — `exec` hard-codes `approval_policy: Never`, which is the intended behaviour and makes credential scoping the entire safety story.
- **The coworker acts unattended.** It runs commands, calls APIs, and opens pull requests without stopping to confirm. This is a product decision, not a limitation worked around — but it means "what needs approval?" is never a valid question, and the only real controls are what the token cannot do, what the sandbox permits, and which tools exist at all.

**Standing preferences for this effort:**

- Plan, don't do. Every ticket resolves a decision. The pull to just build it is the signal the map is finished.
- Prefer the smallest thing that is genuinely a coworker. When a decision can be deferred past v1 without forcing a rewrite, defer it and say so.
- **Sequencing risk: evolving memory.** It is the least well-defined capability in scope and the hardest to call "done". Decide its shape early (it constrains the note model and the retrieval story), but be willing to ship a deliberately thin v1 of it. If the map starts sprawling, this is where it will sprawl.

**Skills every session should consult:** `/grilling` and `/domain-modeling` by default. `/research` for the research tickets. `/prototype` where a design question needs something concrete to react to. `/codebase-design` for the connector-interface and job-model tickets — both are deep-module shape questions.

## Decisions so far

<!-- one line per closed ticket: gist + link. -->

- [Which agent engine does the coworker run on?](issues/01-agent-engine.md) — **OpenAI's Codex CLI.** Open source, locally installed, filesystem-native (the vault is just files it already reads and writes), and an MCP client (so GitHub and Linear are MCP servers). The Slack layer becomes a wrapper around a subprocess. Costs: the stack leaves Anthropic entirely, and it is a coding agent being used for general knowledge work. **Conditional** — reopen if [What can Codex CLI actually do when driven headlessly?](issues/09-codex-cli-headless-surface.md) finds no structured streaming, no session resumption, or no unattended approval mode.
- [What can Codex CLI actually do when driven headlessly?](issues/09-codex-cli-headless-surface.md) — **the engine decision's three reopen triggers are all discharged**; Codex CLI stays. Progress reporting is achievable (item-level JSONL, no deltas in `exec`), restart survival works at **turn granularity**, and unattended operation is the default (`exec` hard-codes `approval_policy: Never`). There is a first-class TypeScript SDK, `@openai/codex-sdk`. Inherited constraints: **non-OpenAI providers are effectively blocked** (`WireApi` has one variant, `Responses`), no semantic guardrails on external actions, no cost ceiling, `AGENTS.md` capped at 32 KiB so it cannot be the memory, and the project ships multiple alphas a day so **pin the version**. Findings: [`research/codex-cli-surface.md`](research/codex-cli-surface.md).
- [How does Slack model a bot that thinks for an hour?](issues/02-slack-surface-research.md) — `app_mention` is the only viable primitive (slash commands are barred from threads; the Assistant surface is DM-only). 3-second ack then queue; **no expiring token**, so the bot can write to the thread indefinitely — dedupe on `event_id`. `assistant.threads.setStatus` now works in channels but **times out after two minutes**, so long jobs need a sub-2-minute heartbeat. Rate limits favour editing one message in place. Socket Mode is right for a self-hoster. Bolt auto-acks before the listener runs, but `processBeforeResponse: true` (and therefore any FaaS deployment) causes **four duplicate runs**. Findings: [`research/slack-surface.md`](research/slack-surface.md).
- [Which Codex interface: `exec` + SDK, or `app-server`?](issues/11-codex-interface.md) — **`codex exec` via `@openai/codex-sdk`.** The coworker does not stop to ask permission — it runs commands, calls APIs and opens PRs unattended — which removes `app-server`'s only decisive advantage and lands on the stable, Apache-2.0, TypeScript-native path. Given up: mid-turn `turn/steer` (hard-stop is retained — the wrapper owns the subprocess), delta streams, and `dynamicTools`. Consequence: **the token is the permission model** → [With no approval gate, what bounds the blast radius?](issues/12-blast-radius.md). Recorded as [ADR-0001](../../docs/adr/0001-codex-cli-via-exec-and-sdk.md).
- [Provision a Slack app, a test workspace, and GitHub/Linear tokens](issues/05-provision-accounts-and-tokens.md) *(partial — Slack app outstanding)* — both servers accept bearer credentials. Live inventory measurements established that MCP annotations are not a portable safety primitive: GitHub marked only `delete_file` destructive while merge and push were unmarked. GitHub now uses a repository-scoped fine-grained PAT through its official MCP server ([ADR-0007](../../docs/adr/0007-github-is-an-official-mcp-server.md)); Linear uses its API key. Inventories: [`linear-mcp-inventory.md`](research/linear-mcp-inventory.md), [`github-mcp-inventory.md`](research/github-mcp-inventory.md).
- [With no approval gate, what bounds the blast radius?](issues/12-blast-radius.md) — **the credential is the boundary; exact disabled tools are defence-in-depth.** The coworker may do anything a human can undo, but known merge, approval, repository-file deletion, and Linear deletion tools are removed. Full inventories are not pinned: upstream capabilities may evolve without stopping the service. GitHub's fine-grained PAT limits repository reach, while branch protection remains a repository-side backstop where available. Recorded as [ADR-0002](../../docs/adr/0002-unattended-action-boundary.md).
- [How does a delegated job actually run?](issues/08-job-model.md) — **one Session per Slack Thread**, resumed on each mention; the wrapper's only state is a `thread_ts → codex thread_id` mapping. **Cross-Thread context goes through the Vault and only the Vault** — Sessions never read each other, because Threads have different audiences and transcript access would put a private channel one grep from a public answer. Follow-up mentions **queue at the Turn boundary**. Progress and audit are **two channels with opposite semantics**: one status message edited in place (driven by Codex's `todo_list`, refreshed inside Slack's 2-minute `setStatus` timeout) plus **every Write appended permanently**, since the Thread is the only accountability record. Bounds (wall-clock, max-Turns, token budget) are entirely the wrapper's — Codex offers none. Vocabulary written to [`CONTEXT.md`](../../CONTEXT.md).
- [What is a note, and what is a memory?](issues/06-note-vs-memory-domain-model.md) — **there is no memory store; the Vault is the memory.** One artifact: everything the coworker writes is a Note, and those Notes are what it remembers. Recall is **agent-initiated traversal of the wikilink graph**, not preloading — with one small **Root note** injected into every Job as the entry point, because exploration answers *how* to find things but not *whether it looks*. The coworker is its own **Librarian**, filing and linking in a short Turn at the end of each Job. `AGENTS.md` stays the stable operating manual and is never the memory. Recorded as [ADR-0003](../../docs/adr/0003-vault-is-the-memory.md); vocabulary in [`CONTEXT.md`](../../CONTEXT.md).
- [What stops untrusted content from becoming trusted memory?](issues/10-memory-poisoning.md) — **visibility over gating for Notes; a structural constraint on the one file that is prompt.** External content reaches the Vault freely, with provenance in frontmatter and **every Note diff echoed into the Thread**, so a poisoning attempt is visible where the human is already reading. Quarantine was rejected because the Librarian is the same agent that just read the poisoned issue. The acute case is the **Root note**, injected into every Job in every Thread: its grammar is **links-only, enforced by the wrapper at injection**, so a compromised Job can add a link but cannot write instructions into the prompt. Recorded as [ADR-0004](../../docs/adr/0004-root-note-is-links-only.md).
- [Connector interface: MCP servers, a plugin API, or both?](issues/07-connector-interface.md) — **MCP direct; connectors are configuration, not code.** Codex calls servers itself, so a wrapper abstraction would require a proxy server, while normalising GitHub and Linear would erase real domain differences. Third-party extension is one new `mcp.json` entry. [ADR-0007](../../docs/adr/0007-github-is-an-official-mcp-server.md) restores GitHub to this rule after the superseded ADR-0006 experiment.
- [What is the real integration surface for GitHub and Linear?](issues/03-github-linear-surface-research.md) — both publish MCP servers with bearer-token authentication and different domain shapes. Repo work favours a local checkout because APIs cannot grep or run tests: use local `git` for checkout and push, then GitHub MCP for metadata and pull-request creation. GitHub uses a repository-scoped fine-grained PAT; accepted limitations of that token define which optional search workflows are available. Findings: [`research/github-linear-surface.md`](research/github-linear-surface.md).
- [How do agents actually accumulate and recall memory?](issues/04-memory-patterns-research.md) — every real system converges on **a small always-loaded index plus a corpus loaded on demand**; the index is the *trigger*, and without one memories exist but never surface. Almost nobody does embedding retrieval — it is agent-initiated grep plus an index. Notes and memories share a mechanism but not a policy (three frontmatter fields and one index file, not a second store). Hard budget: Codex silently truncates `AGENTS.md` at **32 KiB**. Nobody has solved decay. Findings: [`research/agent-memory-patterns.md`](research/agent-memory-patterns.md).

## Not yet specified

In scope, but not yet sharp enough to ticket. Graduates as the frontier advances.

- ~~**What is worth writing down**~~ — **settled by refusing to settle it**, on [`build/07`](build/07-the-vault.md#decision-the-taxonomy-is-the-librarians-and-it-looks-before-it-writes). It is judged by the Librarian per Job, not by a rule: the pass is handed the transcript and the Root note and told that writing nothing is a complete outcome. The one thing made structural is that it **searches before it writes** and updates by preference — which is a prerequisite rather than a courtesy, since a Note is the current belief and there is no rewriting one in place without first finding it.
- ~~**Vault conventions**~~ — **no taxonomy ships and none is enforced** ([`build/07`](build/07-the-vault.md)). The wrapper states invariants (one topic per Note, reachable from a hub, Root is links-only, filename is the title) and the structure is the Librarian's, which stabilises by imitation because each pass reads the Vault as it currently stands. Frontmatter is exactly `modified`, `thread`, `job`, stamped by the wrapper onto the Notes that changed.
- **Concurrent writers to one Vault** — the layout question is answered above, and a hand-edit between Jobs is respected and tested. What is *not* settled is who wrote a file when more than one writer is active. Between Jobs, [`build/07`](build/07-the-vault.md) detects the overlap and reports the change as unattributed rather than guessing; for a **human** editing while a Job runs it cannot even detect it, so their edit is recorded as the coworker's Write. Both would be closed by per-writer information the filesystem does not carry.
- **Persistence** — narrowed sharply: Codex owns Session state (append-only rollouts on disk) and the Vault is files, so the wrapper's only durable state is the `thread_ts → codex thread_id` mapping. What holds that mapping, and whether Slack's own thread history makes a separate Job record unnecessary. **Build/06 added a second candidate**: the per-Thread queue is in memory, so a restart loses queued mentions silently after Slack has already been ack'd.
- **Session lifecycle at the edges** — retention and pruning of `~/.codex/sessions` (no documented upstream policy), and what happens to a Session when its Thread is archived or deleted.
- **Configuration schema and setup story** — what a self-hoster must supply, and how they supply it.
- **Deployment shape** — how someone actually runs this. Docker, a bare Node process, something else.
- **Identity mapping** — **tested live** (ticket 05): `User.gitHubUserId` is real and populated, but **only for users who have linked GitHub to Linear** — 3 of 16 in a real workspace. The numeric id resolves to a login cleanly. So the join is free where it exists and absent otherwise; the open question is now narrower — what the coworker does for the majority of users who are *not* linked.
- ~~**GitHub token type**~~ — **settled as a fine-grained PAT** limited to selected repositories and only the permissions required by the configured GitHub MCP toolsets ([ADR-0007](../../docs/adr/0007-github-is-an-official-mcp-server.md)). Reduced setup and one connector path are preferred over owning an App token-minting lifecycle; workflows unavailable to the scoped token are accepted rather than recovered with a broader credential.
- **Cost and model policy** — narrowed sharply by the Codex research. "Bring your own model" is **effectively not available**: `WireApi` has one variant and any alternative backend must serve an OpenAI Responses API. Codex provides **no budget ceiling and no max-turns kill switch** — usage is reported after the fact — so any spend bound must be enforced by the wrapper. [`build/05`](build/05-bounds-and-failure.md) provides an opt-in per-Turn wall clock, Turn cap, and token budget; all configured limits and manual stop reduce to aborting the run. They are disabled by default. The instance-wide concurrency ceiling remains four via [`build/06`](build/06-queue-at-turn-boundary.md), derived from Slack's `chat.update` allowance.
- **Codex version pinning and upgrade policy** — Codex ships multiple alpha releases per day and has already removed flags this project would plausibly have depended on (`--full-auto`, `wire_api = "chat"`, `ollama-chat`). Self-hosters install and forget. What version is pinned, how upgrades are tested, and who carries that burden.
- **Session storage hygiene** — `~/.codex/sessions` has no documented retention or pruning policy, and `--ephemeral` silently disables persistence entirely. Whoever owns durability owns this.
- **Auth mode for an always-on bot** — whether ChatGPT-plan authentication permits it, or whether an API key is required. Flagged as unestablished by the Codex research rather than guessed; likely resolved by ticket 05.
- **Output adaptation** — Codex CLI is a coding agent. What does the Slack layer have to do to its output before a human reads it in a thread, and how much of the coworker persona lives in `AGENTS.md` versus in the wrapper? **Half-answered by [build/03](build/03-progress-status-message.md)**: the *progress* half sits in the wrapper — the status message's shape, its icons, its escaping of model-authored text — because its content is the event stream rather than prose. The *answer* half is still the model's, posted verbatim, and still fog.
- **Testing strategy for an agent** — what a meaningful test even is here.

**Graduated out of the fog:** the permission model is now [With no approval gate, what bounds the blast radius?](issues/12-blast-radius.md) — reshaped by the interface decision, since "what needs confirmation" is no longer a question that can be asked.

## Out of scope

Ruled beyond the destination. Returns only if the destination is redrawn, and then as a fresh effort.

- **Multi-tenant SaaS** — Slack app distribution, OAuth install flows, per-workspace token storage, tenant-isolated memory, billing, Slack app review. Ruled out by the open-source self-hosted decision.
- **Acting unprompted** — channel watching, GitHub/Linear webhooks, schedulers, "this PR has been stale 3 days". Ruled out by the delegate-and-walk-away reading of AFK. The largest single thing not being built.
- **Open-source release plan** — licence, README and setup docs, contribution model, third-party connector authoring. Real work, but it follows the spec rather than shaping it; the destination is a buildable spec, not a publishable repo.
- **Non-Slack surfaces** — Discord, Teams, a CLI, a web UI. Slack is the product surface for v1.
